**Definition of ported**: A Python function delegates its core business logic to a native C++ function via `_ifcopenshell_capi`.

## Public IFCAPI documentation

Comments on public declarations in `src/ifcapi/include/ifcapi/bindings/` are
part of the cross-language API contract. They are propagated into generated
bindings and their documentation, so write them as concise Doxygen comments
that remain correct in every target language. Document fields on public option
and result structures as carefully as functions.

Use language-agnostic, semantic wording: say “when omitted” or “no result”
instead of source-language sentinels, and describe lists, mappings, and IFC
entities rather than container or smart-pointer implementation types. Explain
observable behavior rather than the algorithm used to implement it. Preserve
the contract details users need, including units, coordinate systems, ordering,
uniqueness, mutation and side effects, schema restrictions, defaults,
precedence, absence behavior, and ownership or lifetime where relevant.

Before documenting or changing a contract, verify the behavior against the
native implementation, the upstream Python behavior, and focused tests. Do
not infer or promise behavior that cannot be verified. Update the declaration's
documentation whenever its public behavior changes. Generated documentation
and generated binding output must be regenerated by the normal workflow; never
edit generated files directly.

## Cross-Target Callsite and Test Synchronisation

The native `ifcapi` contract and its generated target-language bindings must
remain synchronised. When an `ifcapi` source symbol is added, removed, renamed,
or changes its parameter or return shape, update every affected target-language
callsite and test in the same change. Do not leave Python, TypeScript, WASM, or
other generated-binding consumers referring to the previous contract.

For a newly ported API module or operation:

- Add representative tests to `packages/ifcopenshell-js/` for the generated
  TypeScript/WASM API. Exercise the public high-level API and verify observable
  IFC behaviour, including relevant option encoding, handle conversion,
  nullability, returned collections, and resource disposal.
- Update existing TypeScript test callsites whenever a native symbol or public
  binding shape changes. Regenerate the bindings before editing generated-call
  expectations; never patch generated output directly.
- In the `ifcapi`-backed `ifcopenshell-python`, reuse the existing upstream
  parity test where one already covers the operation. Replace its internal or
  legacy implementation call with the new native `_ifcopenshell_capi`-backed
  path while preserving the public Python API and the test's behavioural
  assertions.
- Add focused Python parity coverage when no existing test exercises the full
  native behaviour. A passing TypeScript smoke test does not replace Python
  parity coverage, and an existing Python test does not replace target-language
  marshalling coverage.

After all source and callsite changes are complete, regenerate once and run the
focused native Python and TypeScript/WASM suites.
